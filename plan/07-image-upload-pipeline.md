# 07 · 프라이버시 업로드 파이프라인 · 다운스케일 · 콘텐츠 해시

> AI 전송 전, 고정된 순서로 EXIF를 로컬에서 읽고 원본을 JPEG로 재인코딩(EXIF 제거 보장)한 뒤 다운스케일본만 업로드한다. 이 스트림에서 콘텐츠 해시를 1회 계산한다.

- **Epic**: Analysis
- **Depends on**: 04, 06
- **PRD**: §5 프라이버시, §9 #15, §4.7(해시 시점)
- **Prototype**: 없음(비가시 파이프라인)

## 목표
프라이버시 계약을 코드로 못박는다: **원본 EXIF는 로컬에서만 읽고, 외부로 나가는 이미지는 항상 EXIF가 제거된 다운스케일 JPEG**. 동시에 캐시 키용 해시를 중복 I/O 없이 계산.

## 전송 파이프라인 순서 (§5 — 고정, 위반 금지)
1. **① 원본에서 GPS/시각 EXIF 로컬 읽기** (06 로직 호출).
2. **② 다운스케일 = JPEG 재인코딩** (해상도 축소 + JPEG 인코딩).
3. **③ 업로드** (08 VisionProvider로 전달).

- [ ] 이 순서를 **단일 함수/파이프라인 컴포넌트**로 캡슐화해 호출부가 순서를 어길 수 없게 한다.

## EXIF 제거 보장 (§5 — 핵심)
- [ ] **모든 원본을 포맷 무관 업로드 전 항상 JPEG로 재인코딩**한다. 이 재인코딩이 EXIF 제거를 보장.
- [ ] `ExifInterface`의 스트립에 의존하지 않는다(JPEG 전용이라 HEIC/RAW엔 동작 안 함). 재인코딩을 EXIF 제거의 단일 보장 수단으로 삼음.
- [ ] 검증: 재인코딩 산출물에 GPS/시각 EXIF가 없음을 테스트로 확인(HEIC/RAW 입력 포함).

## 다운스케일
- [ ] 업로드용 목표 해상도/품질 결정(인식 정확도 vs 업로드 비용·속도). 예: 장변 ~1024px, JPEG q~80 (리뷰에서 확정).
- [ ] 큰 원본(HEIC/RAW/대용량 JPEG) 디코딩 시 `inSampleSize`로 메모리 안전 로딩, OOM 방지.
- [ ] 산출물은 메모리/임시 파일로 관리하고 업로드 후 정리(원본 로컬 저장 정책은 §5 "결과는 기기 로컬만").

## 콘텐츠 해시 (§4.7 해시 시점 — 핵심)
- [ ] **선택 직후 일괄 해싱하지 않는다.** 이 파이프라인이 사진을 스트림으로 읽는 김에 해시를 **1회 계산**(중복 I/O 회피, §5 성능 예산).
- [ ] 해시 대상·알고리즘 확정(원본 바이트 기준 권장; 04와 합의). 결과를 04 `CacheRepository`에 저장/조회.
- [ ] **캐시 hit면 다운스케일·업로드·AI·지오코딩을 스킵**(10 오케스트레이터가 파이프라인 진입 전 캐시 확인).

## 핵심 결정·제약
- 파이프라인 순서는 계약이다 — ②/③ 사이에 원본을 그대로 업로드하는 경로가 존재하면 안 됨.
- GPS 있는 사진(06에서 `source=GPS`)은 애초에 AI 전송 대상이 아니므로 업로드하지 않는다(비용·프라이버시 절감).
- 해시 계산은 GPS 유무와 무관하게 캐시 키로 필요하므로, 스트림 1회에서 함께 산출.

## 완료 조건 (DoD)
- [ ] 업로드 산출물에서 EXIF(특히 GPS/시각)가 제거됨을 JPEG/HEIC/RAW 입력 모두에서 검증.
- [ ] 파이프라인이 ①→②→③ 순서를 강제(호출부가 순서를 바꿀 수 없음).
- [ ] 사진 스트림 1회 읽기로 해시가 계산되고 재사용됨(I/O 중복 없음 로깅 확인).
- [ ] 대용량/HEIC/RAW에서 OOM 없이 처리.

## 리스크·주의
- HEIC 디코딩은 기기/OS 지원에 의존 — 저지원 기기 폴백 필요.
- 다운스케일 과도 시 랜드마크 인식률 저하 → 해상도/품질은 08 인식률과 튜닝 루프.
- 해시 알고리즘 선택(전체 vs 부분)은 충돌 위험 vs 속도 — 04 스키마와 함께 확정하고 역기록.
